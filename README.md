# GrantNavigator
Данный проект создан в ходе изучения курса разработки полного цикла. Первоначально взятая идея проекта звучит так: "Грантовый кабинет: создание заявок, отслеживание дедлайнов, ИИ-проверка соответствия критериям конкурса". В репозитории ведутся обновления README, помимо базовых компонентов он содержит записи типа "лайфстайл" для простоты понимания.

Проект состоит из 5 лабораторных работ, выполняются они последовательно, расширяя проект. Ниже будет вестись описание разработки.

## Лабораторная 1. Интерфейс приложения и каркас frontend.

*Цели работы*:
- Определить основные экраны и пользовательские сценарии проекта;

### Шаг 1. Определите назначение приложения, основные пользовательские сценарии и необходимые экраны. 
#### Назначение приложения:
Грант.Навигатор - веб-приложение для участников грантовых конкурсов. Оно предназначено для организации работы с грантовыми проектами: поиска подходящих конкурсов, подготовки заявок, контроля сроков подачи и предварительной проверки заявки на соответствие требованиям выбранного конкурса.

Приложение позволяет пользователю хранить свои проекты, связывать их с подходящими грантовыми конкурсами и отслеживать процесс подготовки заявки. При подготовке заявки есть доступ к ИИ-ассистенту, который проверяет её относительно требований выбранного грантового конкурса. Проверка включает наличие необходимых разделов и информации, соответствие установленным требованиям, а также оценку качества и полноты сформулированного содержания. По результатам проверки пользователь получает перечень обнаруженных проблем и рекомендации по доработке заявки.

#### Пользовательские сценарии:
1. Регистрация и настройка профиля:
   - пользователь регистрируется в системе, указывает необходимые персональные данные и подтверждает согласие на обработку данных;
   - пользователь может указать интересующие направления грантов, чтобы в дальнейшем использовать их при подборе подходящих конкурсов;
   - после всего цикла регистрации он получает доступ к основному функционалу приложения.
2. Создание и редактирование проекта:
   - пользователь переходит в раздел со своими проектами и создаёт новый проект;
   - в проекте пользователь заполняет основные сведения о своей инициативе: название, описание, цели, задачи и другие необходимые данные;
   - проект можно сохранить, вернуться к его редактированию и использовать при подготовке заявок на различные грантовые конкурсы.
3. Поиск и выбор грантового конкурса:
   - пользователь просматривает доступные грантовые конкурсы и выбирает подходящий конкурс;
   - для поиска конкурса пользователь может использовать фильтры и текстовый поиск;
   - в карточке конкурса отображается основная информация: название, описание, требования к участникам, критерии оценки и срок подачи заявки;
   - после выбора конкурса пользователь может начать подготовку заявки и связать конкурс с одним из ранее созданных проектов;
   - создаётся заявка, связанная с выбранным конкурсом и проектом пользователя.
4. Подготовка и проверка заявки:
   - пользователь открывает выбранный конкурс и связанную с ним заявку;
   - на этапе подготовки пользователь редактирует содержание заявки в соответствии с требованиями конкурса. После заполнения заявки пользователь может запустить проверку с помощью ИИ-ассистента.
   - ИИ-ассистент анализирует содержание заявки относительно известных требований и критериев выбранного конкурса и формирует результат проверки: выявленные несоответствия, недостаточно раскрытые пункты и рекомендации по улучшению заявки;
   - пользователь вносит необходимые изменения и при необходимости повторяет проверку.
5. Контроль сроков и статуса заявки:
   - пользователь отслеживает свои заявки и сроки подачи в отдельном разделе;
   - для каждой заявки отображается информация о выбранном конкурсе, сроке подачи и текущем статусе. Например, могут использоваться следующие статусы (пока считаем, что изменение статуса осуществляется вручную):
      - Подготовка: заявка находится в процессе заполнения;
      - Готова к подаче: подготовка заявки завершена;
      - Подана: заявка отправлена на конкурс;
      - Рассматривается: заявка находится на рассмотрении организаторами;
      - Результат получен: по заявке опубликован результат конкурса.

ИТОГОВЫЙ ЖИЗНЕННЫЙ ЦИКЛ ЗАЯВКИ: 
```
Регистрация → создание проекта → поиск конкурса → выбор конкурса и проекта → подготовка заявки → проверка соответствия → доработка → подача заявки → отслеживание результата
```

scripts/
  create_tables.py  создаёт таблицы в БД

| `grant_sections` | Обязательный раздел заявки конкретного конкурса (например, «Бюджет») | М:1 к `grants` |
| `projects` | Проект пользователя | М:1 к `users`; 1:М к `applications` |
| `applications` | Заявка — связывает проект и конкурс | М:1 к `grants`, `projects`, `users`; 1:М к `application_answers`, `check_results` |
| `application_answers` | Текст пользователя по одному разделу заявки | М:1 к `applications` и `grant_sections` |
| `check_results` | Один запуск ИИ-проверки заявки (история проверок сохраняется) | М:1 к `applications`; 1:М к `check_issues` |
| `check_issues` | Одна строка результата проверки (замечание по разделу) | М:1 к `check_results` |

Все связи реализованы через внешние ключи (`ForeignKey`) с каскадным удалением: удаление проекта удаляет его заявки, удаление заявки удаляет её ответы и историю проверок.

### Шаг 4.	Реализуйте создание, чтение, изменение и удаление данных для основных сущностей проекта. Операции должны работать с PostgreSQL через SQLAlchemy.

Отдельно: `PUT /applications/{id}/answers` сохраняет ответы по разделам, `POST /applications/{id}/check` запускает ИИ-проверку (пока по простым демо-правилам: пустой раздел — ошибка, короткий — предупреждение; настоящую модель подключим позже).

## Лабораторная 3. Архитектура frontend и динамический интерфейс.
*Цели работы*:
- Реализовать интерактивное поведение основных экранов приложения;
- Выстроить понятную модульную структуру frontend.

### Шаг 1. Организуйте код приложения по страницам, пользовательским действиям, предметным сущностям и общим компонентам. Убедитесь, что у каждого модуля понятное назначение и в коде нет дублирования.

В лабораторной 1 код лежал в плоских папках (`components`, `pages`, `context`, `data`, `utils`, `types`). Для небольшого каркаса этого хватало, но с появлением форм, проверок и состояний загрузки такая структура быстро превращается в свалку. Поэтому frontend разложен на пять слоёв:

| Слой | Назначение | Что лежит внутри |
| --- | --- | --- |
| `app` | Конфигурация приложения | точка входа, карта маршрутов, провайдеры (тема, уведомления, роутер), каркасы страниц |
| `pages` | Экраны | 11 файлов-страниц; только «сборка» экрана из готовых частей |
| `features` | Действия пользователя | «войти», «создать проект», «запустить ИИ-проверку», «удалить заявку» и т.д. |
| `entities` | Предметные сущности | конкурс, проект, заявка, пользователь: типы, функции API, карточки |
| `shared` | Общий код без привязки к предметной области | UI-кирпичики, хуки, валидаторы, имитация сети |

Чтобы не было дублирования, одинаковые вещи вынесены в `shared` и используются повсюду:
- один хук `useForm` и один набор валидаторов обслуживают все 8 форм приложения;
- один компонент `AsyncBoundary` решает, что показать на любом экране с данными: загрузку, ошибку, «нет данных» или сами данные;
- один `ConfirmDialog` используется для всех удалений;
- карточки конкурса и проекта не знают про кнопки: действия («Участвовать», «Удалить») передаются в них снаружи, из слоя `features`.

### Шаг 2. Выберите структуру проекта (например, упрощённый Feature-Sliced Design: app, pages, features, entities, shared). Кратко опишите выбранную структуру в README.

Выбран упрощённый Feature-Sliced Design (FSD). Полная спецификация не соблюдается: например, нет слоя `widgets`, а логика небольших страниц живёт прямо в файле страницы.

Структура фронтенда:
```
frontend/src/
  app/                          конфигурация приложения
    main.tsx                    точка входа
    App.tsx                     карта маршрутов (адреса из лабораторной 1)
    providers/AppProviders.tsx  тема MUI, уведомления, роутер
    layouts/                    каркасы страниц: AppLayout (с меню), AuthLayout (без меню)
    styles/theme.ts             единая тема оформления MUI
  pages/                        по одному файлу на экран
    RegistrationPage, InterestsPage, GrantsPage, GrantDetailPage, ProjectsPage,
    ProjectCreatePage, ProjectDetailPage, ApplicationsPage, ApplicationEditPage,
    ProfilePage, NotFoundPage
  features/                     пользовательские действия
    auth/                       вход, регистрация, восстановление пароля
    interests-edit/             выбор интересов (страница интересов и профиль)
    grant-search/               поиск и фильтры каталога
    participate-in-grant/       кнопка «Участвовать» и окно выбора проекта
    project-form/               форма создания и редактирования проекта
    project-delete/             удаление проекта (вместе с его заявками)
    application-edit/           форма заявки по разделам конкурса
    application-status/         смена статуса и фильтр заявок по статусу
    application-check/          панель ИИ-проверки заявки
    application-delete/         удаление заявки
    profile-edit/               личные данные и смена пароля
    demo-mode/                  демо-панель: имитация сбоя сети, сброс данных
  entities/                     предметные сущности
    grant/  project/  application/  user/
      model/                    типы TypeScript и константы
      api/                      функции работы с данными (пока имитация сервера)
      ui/                       карточки и значки сущности
      lib/                      вспомогательные функции
  shared/                       общий код
    ui/                         PageHeader, ConfirmDialog, уведомления, анимации,
                                состояния загрузки / ошибки / «нет данных»
    lib/                        useForm, валидаторы, useAsync, useAsyncAction, работа с датами
    api/                        имитация сети (задержка и сбой), хранилище в localStorage
```

Правила, которые соблюдаются в коде:
- слой может импортировать только слои **ниже** себя: `app → pages → features → entities → shared`;
- срезы одного слоя друг друга не импортируют (одна feature не берёт код из другой);
- снаружи срез доступен только через свой `index.ts` (публичный интерфейс);
- импорты идут по алиасу `@/…` (например, `@/shared/ui`), а не по цепочкам `../../../`.

Что изменилось по сравнению с лабораторной 1: синхронное хранилище в памяти (`context/AppContext`) заменено асинхронным имитированным API (`shared/api` и `entities/*/api`). Без этого нельзя было показать состояния загрузки и ошибки. Подключение к настоящему backend (лабораторная 2) запланировано на следующий этап: достаточно заменить функции в `entities/*/api`, остальной код менять не придётся.

### Шаг 3. Реализуйте ключевые интерактивные элементы: формы, управление состоянием компонентов, реакцию интерфейса на действия пользователя. Используйте TypeScript для типов данных и свойств компонентов.

Реализовано:
- **Формы** с проверкой полей: вход, регистрация, восстановление пароля, интересы, проект, заявка, личные данные профиля, смена пароля.
- **Каталог**: поиск по тексту (с задержкой 250 мс, чтобы не фильтровать на каждую букву), фильтр по направлению, переключатель «Только рекомендованные», кнопка «Сбросить».
- **Окно «Участвовать»**: список проектов загружается при открытии; без выбора проекта «Продолжить» подсказывает, что нужно выбрать; из проекта и конкурса создаётся заявка и открывается её редактор.
- **Редактор заявки**: счётчики символов, индикатор заполненности, метка «Есть несохранённые изменения», кнопка «Сохранить» активна только при изменениях, предупреждение браузера при закрытии вкладки с несохранёнными правками.
- **ИИ-проверка**: запуск, индикатор ожидания, результат с процентом и замечаниями по разделам, повторный запуск; проверка блокируется, пока в заявке есть несохранённые правки (она работает с сохранённым текстом). Сама проверка пока демонстрационная (по длине текста разделов), настоящая модель подключается позже.
- **Статус заявки** меняется вручную сразу, а при ошибке откатывается назад с уведомлением. В списке заявок статусы можно фильтровать.
- **Удаление** проекта и заявки через окно подтверждения; при удалении проекта удаляются и его заявки.
- **Уведомления** внизу экрана: «Проект создан», «Изменения сохранены», сообщения об ошибках.
- **Состояние компонентов**: локальное состояние (`useState`) и три универсальных хука: `useForm` (форма), `useAsync` (загрузка данных при открытии экрана), `useAsyncAction` (действие пользователя: «выполняется», «ошибка», результат). Профиль пользователя читается через `useCurrentProfile`, поэтому аватар в шапке и рекомендации в каталоге обновляются сразу после изменения профиля.

Типизация: типы данных описаны в `entities/*/model/types.ts` (`Grant`, `Project`, `Application`, `CheckResult`, `UserProfile` и др.), у каждого компонента есть интерфейс свойств `Props`, универсальные хуки типизированы обобщениями (`useForm<V>`, `useAsync<T>`, `AsyncState<T>`).

### Шаг 4. Реализуйте клиентскую валидацию форм и понятные сообщения об ошибках ввода. Для экранов с данными учтите состояния загрузки, ошибки и отсутствия данных.

#### Валидация форм
Проверки собраны в `shared/lib/validators.ts` (обязательное поле, длина, email, формат, совпадение значений, согласие, непустой список), а хук `useForm` применяет их к полям. Ошибка поля появляется после ухода с поля и затем обновляется при вводе; при отправке проверяется вся форма. Ошибки «от сервера» (логин занят, неверный текущий пароль) показываются под нужным полем.

| Форма | Основные правила |
| --- | --- |
| Вход | логин и пароль обязательны; неверная пара — сообщение «Неверный логин или пароль» |
| Регистрация | имя и фамилия 2–50 символов; корректный email; логин от 3 символов, только латиница, цифры и `_ . -`; пароль от 8 символов, буква и цифра; подтверждение пароля совпадает; согласие обязательно; занятые логин или email — ошибка под полем |
| Восстановление пароля | корректный email |
| Интересы | выбрано хотя бы одно направление; выбрана сфера деятельности |
| Проект | название 3–120 символов; краткое описание до 300; цель от 10 символов; целевая аудитория обязательна; счётчики символов |
| Заявка | каждый раздел не длиннее 5000 символов |
| Профиль | те же правила, что при регистрации; занятые логин или email — ошибка под полем |
| Смена пароля | верный текущий пароль; новый от 8 символов с буквой и цифрой; повтор совпадает |

#### Состояния экранов с данными
Компонент `AsyncBoundary` (`shared/ui/states`) показывает одно из состояний:

| Состояние | Что видит пользователь | Где проявляется |
| --- | --- | --- |
| Загрузка | серые заглушки (скелетоны), повторяющие форму будущего содержимого | каталог, конкурс, проекты, заявки, редактор заявки, окно выбора проекта |
| Ошибка | понятное сообщение и кнопка «Повторить»; для «не найдено» — ссылка назад | все экраны с данными |
| Нет данных | пояснение и кнопка следующего действия | нет проектов, нет заявок, ничего не найдено по фильтру, нет заявок с выбранным статусом |

Чтобы показать состояние ошибки без остановки сервера, в нижней части экранов с меню есть панель «Демо-режим» с переключателем «Имитировать сбой сети». Там же кнопка «Сбросить демо-данные». После подключения backend эта панель будет убрана.
